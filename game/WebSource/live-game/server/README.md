# Likerts Live backend

This service owns only `/play`, `/play/*`, and `/api/live/*`. It does not modify the existing static game homepage, survey `/surveys`, `/docs`, `/app`, survey database, SDKs, Messages codecs, or survey authentication. It implements separate mind-reading v1 and creator-quiz v2 modes. [PROTOCOL.md](../PROTOCOL.md) describes v1 and shared transport; the [M2 contract](../../../M2-CONTRACT.md) defines quiz mode. `protocol.schema.json` / `fixtures/protocol-v1.json` retain v1 projections; `quiz-protocol.schema.json` / `fixtures/quiz-protocol-v2.json` describe quiz projections and synthetic reducer examples. Storage remains schema 3.

This is local candidate source, not a deployed service. Release native Live remains unconfigured, and this design continuation requires its own final source-bound qualification. Historical measurements in the operations guide do not qualify this changed tree. [Launch preparation and open gates](../../../LAUNCH-PREPARATION.md).

## Run locally

Use Node 22.23.4, pinned in `.node-version` (supported engine range `>=22.23.4 <23`). From `live-game`, install with `npm ci --ignore-scripts`. Choose an explicit private local SQLite file outside the source tree, set `LIKERTS_LIVE_SQLITE_PATH` to that path, and run `npm start`. Development binds to loopback on port 4311 by default. `LIKERTS_LIVE_PORT` changes the port. Open `/play/quizzes` for creator/practice/quiz hosting or `/play` for mind-reading hosting and either-mode joining. An explicit comma-separated `LIKERTS_LIVE_ORIGINS` overrides the bound-origin development convenience. SQLite is single-machine development storage; its Node API emits an ExperimentalWarning.

There is no process-memory authority or implicit database fallback. The server never reads the survey service's `DATABASE_URL`. SQLite must be an on-disk file, and production refuses SQLite.

## Production configuration and outstanding deployment work

`NODE_ENV=production` requires the dedicated `LIKERTS_LIVE_DATABASE_URL`, an explicit HTTPS `LIKERTS_LIVE_PUBLIC_ORIGIN`, and exact comma-separated `LIKERTS_LIVE_ORIGINS` including that public origin. `LIKERTS_LIVE_BIND_ADDRESS` controls the service bind address; `PORT` or `LIKERTS_LIVE_PORT` selects its port. HTTPS/WSS must be terminated by the reviewed deployment edge. PostgreSQL uses certificate-verified TLS; insecure SSL URL modes are rejected. No provider, database, credentials, DNS route or deployment is created by this code.

`readServiceConfiguration` validates the explicit `LIKERTS_LIVE_MAX_*` and rate/health variables shown in `../.env.example`; the executable passes those actual limits to both the store and HTTP/WebSocket server. Invalid/fractional values, unsupported production maxima and incompatible host/player/socket bounds reject startup. Production launch ceilings are four rooms,64 sockets per process,12 players per room,26 sockets per room and two sockets per member. The player ceiling is fixed12 in production so the native launch picker remains coherent; individual rooms choose capacity2–12. The room default reserves two leases for all thirteen members, allowing every player and the dedicated host to reconnect while a replaced worker's leases remain within their45-second grace. Other caps can be reduced within their validated ranges, but a lower room cap reduces that full-room reconnect overlap. Four rooms times26 durable room leases bounds authenticated connections at104 across workers; the64-socket guard is per process and does not cap anonymous Function invocations or infrastructure billing. These are conservative policy ceilings, not production capacity or latency guarantees. Raising the operating envelope needs further measurement and a deliberate configuration/code review.

`GET /api/live/catalogue` optionally reports `limits.maxPlayers/defaultCapacity` alongside topic metadata. Development can exercise the engine's50-player ceiling; production cannot enable it through an environment override. Public clients must not infer production capacity from development fixtures.

The adapter initializes dedicated `likerts_live_*` tables/indexes for rooms, admissions, budgets, normalized members, command receipts, socket leases and storage-version metadata. The setup role therefore needs DDL permission in the dedicated game schema. A production operator must decide and verify migration/runtime-role separation before deployment; do not grant a game service survey privileges. Pool size is ten per worker, including a dedicated LISTEN connection. Provider connection capacity, networking, backups, monitoring ownership and retention are deployment gates.

Admission rates use the actual TCP peer address, with no trust in caller-supplied forwarding headers. Persistent bucket keys are SHA-256 digests scoped by operation; raw IP addresses are not written by this application. Behind a proxy, verify the trusted peer-address topology before publishing: blindly trusting `X-Forwarded-For` would defeat admission, while treating every customer as one proxy peer can reject legitimate traffic. No trusted-proxy exception is enabled here.

## Authority, privacy and retries

In mind-reading v1 the reducer owns roster, subject rotation, reviewed prompt selection, deadlines, pause/resume, locks, reveal and distance-based scoring. Its prompts are canonical server-selected catalogue entries, not client-submitted questions or AI. A complete fixed-roster match gives equal prediction opportunities and shared ranks; skipped, timed-out subject or prematurely ended matches remain incomplete/provisional.

Quiz v2 accepts a validated `likerts.quiz` v1 creator document at room creation and stores a detached immutable snapshot. Only capacity is a quiz room setting. All frozen-roster players answer each question; host is an observing controller. `quiz-answer` submits a zero-based choice bound to the exact match/round, and host-only `quiz-reveal` can reveal that question early. Correct answers earn 1,000 points; wrong/missing answers zero, without a speed bonus. Inclusive server deadlines and durable receipts prevent late acceptance or duplicate scoring. Quiz mode has no subject/prediction/pause/skip phase. Ending, leaving or removal during an unfinished round redacts its choices/key and finishes incomplete. Disconnect in either mode does not Leave or transfer host authority.

Every host/player has a separate random 32-byte capability. Only its one-way verifier is persisted. Before reveal, host and unrelated players cannot receive the subject answer, other guesses, current-secret-derived scores, raw requests, future prompts, token hashes or admission metadata. Each WebSocket viewer is independently reauthorized and projected, including after cross-worker notifications. Notifications contain only room locator and revision. Fan-out coalesces a burst over 16ms and loads one authoritative room per batch; it does not reuse one member's projection for another member.

Quiz projections expose current question/options, public progress and only the viewer's own submission. Before reveal, even host projections omit correct-answer indices, explanations, future questions and other players' submitted choices. Reveal shares the current question's results only. A creator's uploaded snapshot and exported file already contain its answer key; they are not player projections or invitations.

Commands use HTTP bearer authorization plus UUID `requestId` and exact match/round binding. Receipts store a request fingerprint, never the raw bearer or a cached response. Identical retries do not score or transition again; different payloads using the same ID conflict. A removed player can retry only the identical successful leave receipt, with a terminal response and no room state. An explicit close deletes active room state; subsequent missing-room responses remain terminal.

Create/join use a client-generated admission UUID and independent random 32-byte recovery secret, retained privately before sending. Admission mapping and room creation/join commit atomically. Same-ID/same-payload retries produce one identity and rotate its bearer. `/admissions/recover` verifies the secret and rotates the scoped token atomically without the original payload. Recovery lasts ten minutes and allows at most twenty rotations. Tombstones prevent a lost request resurrecting a closed/kicked/expired membership, and the mapping binds to the immutable room instance, not only its reusable short code. Old bearers and sockets lose authorization. Plaintext admission secrets and bearers are not persisted.

Hosted quiz snapshots, answer keys, explanations and submissions, alongside mind-reading answers/guesses, necessarily exist in the dedicated store. Admission/terminal metadata has separate retention, up to its six-hour lifetime, even after Close deletes active content; recovery itself lasts ten minutes. Deleting active rows does not prove deletion from WAL, backups, database history, user screenshots, hosting logs or client storage. Online-room data flow and actual deployment retention need truthful disclosures; offline-only wording cannot describe this service.

## Resource boundaries and recovery

`app.mjs` exports development `DEFAULT_LIMITS` and conservative launch `PRODUCTION_LIMITS`. Bounds cover the configured player ceiling (12 production;50 development engine), default capacity12, total rooms, sockets per process/per room/per member, body/frame size, queued send bytes, create/join/recovery/read/action/connection/frame/refresh rates and authentication timeout. Shared fixed-window budgets, room quotas, admission mappings, socket leases, action receipts and game state are durable; per-process guards only reject excess work earlier. Unavailable shared admission/storage fails closed. Frames are uncompressed. Invalid frames consume admission too; unsolicited pongs cannot trigger unlimited storage reads.

Quiz creation alone has a bounded 69,632-byte request allowance for the validated document (maximum 65,536 normalized bytes) plus admission envelope. Legacy creation and ordinary requests retain the configured body ceiling (default 8,192 bytes); WebSocket frames retain their default 4,096-byte bound. Creation is HTTP, not a WebSocket command.

Readiness uses one initial aggregate store probe and a single-flight background refresh (default once per five seconds). `GET /api/live/health` reads only that cached snapshot, returning503 for failure or data older than fifteen seconds; it never issues a database query or database-backed rate-budget update per request. `GET /api/live/liveness` reports only process liveness. Both have a local cached-response budget. This bounds anonymous health-query amplification while retaining a meaningful store check. Probe cadence/staleness and the local health budget are explicit validated settings; configure the deployment health checker against readiness with an appropriate frequency and verify proxy peer attribution before publishing.

Deadlines advance on reads/actions and bounded periodic ticks. Mind-reading pause preserves remaining time; quiz mode rejects pause/resume. Room life is capped at six hours, idle rooms at two hours, and finished rooms at fifteen minutes. Cleanup batches are bounded, and reads/actions enforce expiry before cleanup. PostgreSQL uses row transactions, locks and code/revision-only LISTEN/NOTIFY; listener reconnection and periodic projected refresh recover missed notifications. SQLite has no cross-process notification guarantee and is not a production multi-worker adapter.

## Tests and evidence boundaries

`npm run test:backend` runs reducer, SQLite, HTTP/static and opt-in PostgreSQL checks. `npm run test:security` runs the independent HTTP/WebSocket acceptance suite. PostgreSQL tests require the explicit synthetic-only `LIKERTS_LIVE_TEST_DATABASE_URL`; the harness rejects unrelated/non-loopback databases. Tests create their own rows or isolated schema, never survey tables. The root owns the disposable PostgreSQL fixture and its teardown.

`npm test` also includes quiz engine/HTTP/client/UI tests and `test/m2-quiz-privacy.test.mjs`. Final pass/skip counts must come from receipts bound to this candidate; older PostgreSQL or load results do not establish current quiz or hosted execution.

The independent load harness and current measured results are documented in `../operations.md`. Local measurements are evidence for that specific fixture and source fingerprint. They do not establish production concurrency, network latency, high availability, provider failover or recovery from backups. See the parent verification report for final counts and source hashes rather than treating this document as a release certification.

The default `npm test` runs test files sequentially to isolate owned database fixtures and compiler/graphics contention. Concurrency assertions within individual tests (including the 100-mutation PostgreSQL case) are unchanged. Load measurements remain separate, fingerprinted experiments.
