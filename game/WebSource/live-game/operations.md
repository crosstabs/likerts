# Likerts Live operations and evidence

This service is separate from the existing survey service and native offline game. [PROTOCOL.md](PROTOCOL.md) retains mind-reading v1 and shared transport; the [M2 contract](../../M2-CONTRACT.md) defines implemented creator quizzes (protocol 2, modeVersion 1). Both use storage schema 3. Nothing here authorizes deployment, a new provider/credential, paid resources or production-store access. Release native Live remains unconfigured and hosting remains on hold; [launch preparation](../../LAUNCH-PREPARATION.md) records the current local scope and outstanding gates.

## Quiz mode operating scope

- Quiz creation receives a validated immutable creator snapshot, including its key/explanations, through bounded HTTP admission. The quiz-only request ceiling is 69,632 bytes for at most 65,536 normalized document bytes; ordinary body/frame bounds remain separate. Never log uploaded content or credentials.
- Quiz recipients receive current question/options and only their own submission before reveal. Server deadlines, explicit host reveal, immutable locks and durable receipts govern scoring (1,000 correct, zero wrong/missing, no speed bonus). Quiz mode has no subject/predict/pause/skip behavior. Aborted current rounds redact choices/key and award no points.
- Qualify both mode versions through retry, timeout, concurrent final submission, lost acknowledgement, reconnect/background/reload, restart, abort and Leave/Close checks. Include counterfactual key/future-question privacy over HTTP and WebSocket. The v1 load harness/older PostgreSQL runs below do not qualify quiz throughput or the current design source.
- Final design-pass counts and source bindings must come from its final receipts. `npm test` includes quiz engine/HTTP/client/UI and `test/m2-quiz-privacy.test.mjs`; PostgreSQL remains explicit opt-in and skipped cases must remain identified.

## Local verification

From `live-game`, run the v1 independent suite with `npm run test:security`, and quiz-specific checks with `node --test test/backend-quiz-*.test.mjs test/m2-quiz-privacy.test.mjs` (or the complete `npm test`). They use isolated temporary stores, synthetic players, controlled clocks where supported and real HTTP/WebSocket traffic on `127.0.0.1`. SQLite fixtures explicitly select local stores, so deployment environment defaults cannot select a production database. Fetch redirects are rejected. Tests must not reuse survey databases or an existing production store. Fail rather than weaken a bound if secrets leak, revoked access survives, retries score twice or stale commands affect a new match.

PostgreSQL acceptance is explicit opt-in through `LIKERTS_LIVE_TEST_DATABASE_URL`; it is restricted in code to the owned `127.0.0.1:54329/likerts_live_test` fixture, with no user-supplied connection overrides. Each test creates a strictly validated random schema, binds its workers through `search_path`, stops its own processes and drops only that owned schema. It never truncates public tables, touches another database or manages Docker. The two-process checks include a stopped/replaced service after answer lock, cross-process retry/scoring/revocation and shared HTTP admission/action budgets. Process replacement after a committed lock is not a crash during a database commit.

The load harness is `node live-game/scripts/load-test.mjs`. It is restricted to HTTP on `127.0.0.1`, rejects redirects, caps 20 rooms, 50 players per room, 200 total sockets and 60 seconds of workload, and closes only the rooms/sockets it creates. Five further seconds are reserved for teardown; a watchdog emits failure aggregates and exits if teardown stalls. This timer depends on the Node event loop and is not an OS-level CPU kill guarantee. An emergency exit may leave its own synthetic temporary SQLite directory for later cleanup; it never authorizes broad cleanup of other files. Default internal service startup explicitly disables environment database fallback. External-loopback mode is only for an already authorized disposable fixture.

Its JSON output contains aggregates only: no player names, room codes, credentials, answers, guesses or full invite links. A nonzero error count, state-revision regression, unexpected protocol state, source change during the run or incomplete planned workload is material evidence, even when latency is low. It reports HTTP latency, socket authentication, command-to-all-room-snapshots, combined/harness memory and event-loop delay. Pure send-budget boundary tests cover queued bytes plus the next payload; normal reading clients do not prove physical slow-consumer behavior.

## Before any public deployment

Use a dedicated game database and least-privileged game role via `LIKERTS_LIVE_DATABASE_URL`; never fall back to the survey `DATABASE_URL`, survey admission store, export bucket or management authentication. Run game migrations independently and preserve survey routes/data. Production must refuse to start without its configured persistent store and exact browser origin allowlist. HTTPS/WSS termination, trusted-proxy/IP handling and native no-Origin admission need explicit deployment configuration; do not trust arbitrary forwarding headers.

Historical v1 acceptance verified two real PostgreSQL service processes, cross-worker answer privacy, one-score final locks/retries, socket revocation, shared request/socket budgets and a fresh replacement process resuming a committed private answer. Those checks neither qualify the current quiz mode nor prove the deployment topology. Before public deployment, repeat both modes' relevant checks on an authorized isolated deployment with its actual proxy, pooling, TLS and database configuration. Also prove rematch recovery across workers, expiry propagation, preserved deadline recovery and notification-interruption snapshot recovery. Stop a worker during an in-flight command and retry with the same request ID. Graceful replacement after a committed answer does not establish crash-during-commit behavior. Do not treat SQLite evidence as satisfying these gates.

Declare a production operating envelope only after measuring that deployed topology. Budget concurrent rooms, players and sockets together; file descriptors, memory per room/socket, maximum buffered bytes, database pool size/query rate/storage, fan-out traffic, reverse-proxy idle timeout and provider connection/egress quotas all constrain it. The protocol's maximum per-room player count and service ceilings do not imply every room can be full simultaneously. Add load gradually with a fixed runtime and kill switch; obtain authorization before consuming production or paid capacity.

## Monitoring and failure handling

Readiness should indicate store/catalogue availability and schema compatibility without exposing room data. Aggregate counters should cover active rooms/players/sockets, admission rejections by reason, HTTP errors, action latency, transaction conflicts/retries, event-loop delay, publication failures, socket buffered bytes/disconnect reasons and cleanup lag. Do not attach room codes, player identifiers or secrets to metric labels.

Alert thresholds and ownership remain deployment decisions. At minimum alert on persistent store failure, readiness loss, rising action/error latency, sustained admission/backpressure rejection and expiry-cleanup lag. Have a documented operator and escalation route before launch. Reject work explicitly during overload; never accept an action that is not durably applied. After publication loss, clients recover a current projected snapshot rather than replaying internal room records. A host disconnect does not authorize a new host; apply the protocol's recovery rule.

## Retention, privacy and removal

Enforce the protocol's six-hour hard life, two-hour idle expiry and fifteen-minute finished-room expiry on reads/actions as well as bounded background cleanup. Close, kick, leave and expiry must revoke relevant credentials and active subscriptions. Store token verifiers only. Never log request bodies, authorization headers, WebSocket authentication frames, names, answers, guesses or full invite links. Infrastructure access/error logs and tracing need the same review.

`close` deletes active room state. It does not establish deletion from WAL files, database history, backups, crash dumps, traces, browser storage or recipients' screenshots. Publish retention/deletion language only after the actual hosting, backup, logging, browser credential storage and restore policies are defined. The host's room code is an admission locator, not private player authorization. Room participants deliberately receive revealed answers; no technical control can stop participants copying them.

Quiz room content includes creator questions, correct answers, explanations and submissions. Native pending upload recovery also temporarily retains an exact creator copy; it is removed after verified admission. Admission/terminal tombstones have separate bounded retention (up to six hours); successful Close does not immediately erase them. Keep active-content deletion, admission expiry and eventual bounded cleanup distinct in disclosures and operational checks.

## Release and rollback

Pin catalogue hash/version for mind-reading v1 and immutable creator snapshot/modeVersion for quiz v2, with the correct protocol version per room. Reject unsupported modes/versions rather than substituting prompts or interpreting another mode's commands. Test additive migrations and old/new worker interoperability before rolling releases; an older v1-only worker must not receive quiz rooms as if they were catalogue games. Drain sockets and preserve identity on resume. Retain a compatible service artifact and migration rollback/forward plan. A rollback must not restore revoked room access, mutate a frozen quiz snapshot or apply old commands to a rematch.

Public release remains gated on deployment-specific failure/recovery checks, a measured deployment envelope, browser/device end-to-end checks, configured monitoring ownership, explicit retention policy and an authorized deployment. No Kahoot-scale, high-availability, all-copy-erasure or production-capacity claim is supported by local development checks.
