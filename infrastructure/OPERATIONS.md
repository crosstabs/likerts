# Operations and recovery

This runbook describes the implemented local controls and the remaining staging activation. No pager, cloud backup schedule or customer SLA is active. The measured local recovery evidence is [recovery/local-evidence.json](recovery/local-evidence.json); it is a tiny logical PostgreSQL dump, not evidence of a managed recovery time or recovery point.

## Detect and investigate

The service exposes `/internal/metrics` only when `LIKERTS_MONITOR_TOKEN` is configured with a 32–512-character visible ASCII secret. Use a randomly generated secret from the secret manager, separate from user OAuth and service credentials. The process retains an HMAC-derived comparison tag; authorization comparison uses the constant-time HMAC verifier. Keep the endpoint private through ingress and security groups as well as token authorization. Rotate the token in the API and scraper together. Missing or incorrect monitor configuration must be caught by the metrics-availability alert.

Metrics contain only configured route templates, bounded methods and status classes. They contain no workspace IDs, response answers, URLs, query strings or credentials. They count handler responses, not billed responses; retries can increase HTTP counts without increasing revenue. Handler latency excludes response-body transmission. Cancelled handlers release the in-flight count and have a separate counter. Health and metrics requests are excluded from service traffic metrics. Counters reset on process restart; queries use `rate`/`increase`.

[observability/prometheus.yml](observability/prometheus.yml) and [observability/blackbox.yml](observability/blackbox.yml) are internal-network examples. Scrape every ECS task directly with service discovery; scraping only an ALB can hide a failed replica. The health probe separately exercises `/health`, including its database check. Configure actual discovery, private transport and an owned Alertmanager receiver in staging. The rules cover unavailable scrapes, failed or missing health probes, sustained server errors, accepted collection latency and cancelled handlers. The one-percent and 300-ms thresholds are initial internal tuning values, not measured SLO commitments. Low request volume suppresses ratio/latency noise; health alerts remain active. Raw request metrics group 429 with other 4xx responses, so use WAF/ALB status metrics for detailed rate-limit diagnosis.

Run `bash scripts/check-observability.sh` to parse configuration and test healthy/idle, missing-target, sustained-error and high-latency cases using Prometheus 3.5.0. These tests do not prove notification delivery. For the Render launch target, add managed checks for database storage, connections, CPU, HA/failover state and backup freshness; API/worker health and restarts; private export errors; and deletion-journal replication lag. The optional AWS target uses corresponding RDS/ECS/S3 alarms. Explicitly fail an instance, the database connection, and the notification receiver to verify both primary and missing-monitor paths.

## Incident response

1. The responding engineer records UTC detection time, affected region and route, current image digest, migration version and observed customer impact. Assign incident lead and a second recovery reviewer before a data restore. Keep answers, tokens and connection strings out of incident notes.
2. Check the health probe, per-task scrapes, recent deployment, RDS saturation and connectivity. Confirm whether a metric outage is an application outage or a scraper/token failure. Check billed usage in the ledger independently of HTTP request volume.
3. For an isolation, credential or accounting issue, stop affected collection writes and management mutations. Remove public ingress if scope is unknown. Revoke affected credentials and isolate suspect exports. Preserve restricted audit evidence. Do not re-enable writes merely because health is green.
4. For a deployment regression, roll back to a recorded compatible image digest using [README.md](README.md). Confirm that the previous binary supports every applied migration. An image rollback does not roll back the database. Prefer a reviewed forward fix; never edit an applied migration checksum in a live database.
5. Verify a synthetic tenant and a separate tenant: authorization denial across tenants, accepted response and identical retry, one ledger cent, caps, response retrieval and export. Review audit events and rate-limit behavior. Only then restore traffic gradually and observe latency, errors and billing.
6. Record resolution, actual recovery timing/data-loss window, corrective owner and next test date. Send customer or regulator communications only through the authorized incident owner and policy; this repository does not send them.

## Backup and restore discipline

The Render launch design requires the selected paid backup/PITR policy, encryption, access control and a separately durable deletion journal. These deployment requirements still need hosted evidence; Render PITR targeting delay does not establish the prior five-minute data-loss objective. A journal kept only inside the database being restored cannot prove post-snapshot deletions. Export objects expire after 24 hours; restore must never resurrect revoked objects or download capabilities.

Restore into a quarantined database with no public traffic, payment workers or callback workers. Preserve migration owner/runtime separation and forced RLS. Record snapshot/PITR timestamp, last verified independent deletion-journal checkpoint and current credential/membership/settlement checkpoints. If the journal is incomplete, keep restored data inaccessible until the gap is reconciled; do not invent an acceptable loss window. Replay all deletions after the recovery point before granting access. Workspace deletion also requires redacting its survey and response data, clearing management caches and preventing identity re-entry. Revoke restored exports and every old collection capability, OAuth grant and service credential; reissue only after reconciling current authoritative membership and revocation records.

Quarantine every restored callback endpoint and delete restored callback event/idempotency queues before starting callback workers: a snapshot can predate revocation or key rotation. Reconcile current ownership and issue fresh credentials; never resume an old queue automatically. The [callback runbook](webhooks/README.md) documents the worker boundary and signing-key procedure.

Reconcile restored usage, promotional grants, paid purchases, consumption, corrections/refunds/reversals and all processor settlements before starting billing workers. Preserve grant idempotency and quarantine acceptance until post-backup purchases and consumed credits reconcile. Post-backup charges may already have succeeded, and a lost local settlement record must not produce another charge. Compare immutable receipt/usage identifiers and processor idempotency records. Block billing until every ambiguous settlement is resolved. Never infer money owed from HTTP metrics or charge for rejected/duplicate responses.

Apply only the expected immutable migration set; compare SQLx checksums and test the candidate binary. Re-run RLS and scope tests against the restored database. Retain the quarantined original evidence under restricted access until the incident owner approves disposal under retention policy. Measure the entire path through safe reopening when reporting RTO; measure the actual recoverable data boundary when reporting RPO.

## Reproducible local drill

Run `bash scripts/check-recovery.sh`. Docker and Node are required. It builds the immutable runtime candidate and creates only isolated synthetic resources. The container gate first proves migrations, non-root/read-only runtime, restricted-role grants, RLS, authentication and restart durability. The drill then creates two accepted responses, an export and queued callback events, backs up PostgreSQL, deletes one response after the backup and captures the independent deletion journal. It restores to a new database, replays deletion and quarantines every restored capability, verifies the retained response, unchanged two-cent gross ledger and promotional grant/consumption ledger, and proves old credentials/exports cannot be used and restored callback endpoints/queues cannot resume. It checks every applied migration, including response credits and collection-security rate windows, and that forced RLS survives restore.

The failed-migration drill uses a deliberately failing DDL transaction and proves no partial table or migration-state advance. A separate checksum-mismatch drill proves the migration runner refuses altered history. Only this disposable restored copy has its checksum deliberately modified and restored. This is not a production recovery technique.

[recovery/replay.sql](recovery/replay.sql) refuses databases outside the `likerts_recovery_*` namespace. It is a fixture for testing quarantine/replay, not an automated production restore command. It exercises response deletion and a second workspace's tombstoning and survey/version redaction. All local resources created by the harness are removed on completion, including PostgreSQL's anonymous data volume. The written JSON evidence remains available for review. Use `LIKERTS_SKIP_IMAGE_BUILD=1` only when intentionally testing the already-built digest, and record that digest with the result.

Before launch, execute a Render managed restore/PITR recovery including workspace deletion, revoked memberships, credit/payment reconciliation and expired private export objects. Prove journal checkpoint freshness and seven-day backup expiry, measure RTO/RPO against the engineering objectives, exercise a migration failure and compatible image rollback, and deliver a real test alert to the owned receiver. OPS-03 remains open until that evidence exists.
