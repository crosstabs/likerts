# Operations and recovery

The launch deployment is Render Singapore API/MCP/worker, Neon Singapore PostgreSQL and Vercel web/private Blob exports. A named incident responder and delivered alerts remain release gates. The owner declined the managed restore drill on 22 September; no recovery-test spending is authorized, and managed recovery remains unverified. No customer SLA is active. The measured local recovery evidence is [recovery/local-evidence.json](recovery/local-evidence.json); it is a tiny logical PostgreSQL dump, not evidence of managed recovery time or recovery point. Use [render/README.md](render/README.md) for the actual deployment and role boundary; AWS material is an optional alternative only.

## Detect and investigate

The service exposes `/internal/metrics` only when `LIKERTS_MONITOR_TOKEN` is configured with a 32–512-character visible ASCII secret. Use a randomly generated secret from the secret manager, separate from user OAuth and service credentials. The process retains an HMAC-derived comparison tag; authorization comparison uses the constant-time HMAC verifier. Keep the endpoint private through ingress and security groups as well as token authorization. Rotate the token in the API and scraper together. Missing or incorrect monitor configuration must be caught by the metrics-availability alert.

Metrics contain only configured route templates, bounded methods and status classes. They contain no workspace IDs, response answers, URLs, query strings or credentials. They count handler responses, while accepted-response usage is counted separately; retries can increase HTTP counts without increasing accepted responses. Handler latency excludes response-body transmission. Cancelled handlers release the in-flight count and have a separate counter. Health and metrics requests are excluded from service traffic metrics. Counters reset on process restart; queries use `rate`/`increase`.

[observability/prometheus.yml](observability/prometheus.yml) and [observability/blackbox.yml](observability/blackbox.yml) are internal-network examples. Discover and scrape every Render API instance; probing only the public load-balanced URL can hide a failed replica. The public API `/health` includes a database check; the MCP health check verifies gateway configuration/reachability only. Configure actual instance discovery, transport restrictions and an owned Alertmanager receiver. The rules cover unavailable scrapes, failed or missing health probes, sustained server errors, accepted collection latency and cancelled handlers. The one-percent and 300-ms thresholds are internal tuning values, not SLO commitments. Low request volume suppresses ratio/latency noise; health alerts remain active. Raw request metrics group 429 with other 4xx responses, so use provider request metrics and the application limiter's evidence for rate-limit diagnosis. Monitor the callback worker separately; it has no public HTTP health endpoint.

### Public status and alert activation

`/status` and `/api/status` perform timestamped, bounded, unauthenticated probes of the collection API/database, MCP gateway and Clerk public signing keys. They validate expected JSON, refuse redirects and expose no upstream body or exception. Public responses are cached for at most 30 seconds and the page rejects stale results. These probes do not prove OTP delivery, response acceptance, background workers or historical uptime. `/api/health` remains a configuration diagnostic and is not the public status source.

`/api/monitor` is a separate authenticated Vercel function. It is **not scheduled or armed by default**. To activate it after the owner names an approved alert receiver:

1. Obtain a named human responder and approved HTTPS alert receiver. Set `LIKERTS_MONITOR_ARMED=1`, a non-personal `LIKERTS_MONITOR_RESPONDER_ID` identifier, `LIKERTS_ALERT_WEBHOOK_URL` and its exact `LIKERTS_ALERT_RECEIVER_ORIGIN`. Configure a random 32–512-character `CRON_SECRET` through the secret environment mechanism. Missing arming/receiver/responder returns `not_armed`.
2. Configure durable monitor state with `LIKERTS_MONITOR_STATE_REDIS_URL` (an HTTPS Upstash origin), `LIKERTS_MONITOR_STATE_REDIS_TOKEN` and a random 32-character lowercase hexadecimal `LIKERTS_MONITOR_STATE_NAMESPACE`. Use a separate namespace from admission. The monitor refuses to run without state; the state lease serializes runs and bounds notifications to three attempts per event. Receiver acknowledgment is tracked, and a recovery event is emitted after a recorded incident. No raw customer data, receiver URL or responder identity is returned publicly.
3. For authenticated-path coverage, issue a dedicated service credential with only `usage:read` and supply it as `LIKERTS_MONITOR_USAGE_TOKEN`. Verify its scope at issuance; this is not an owner JWT. Set control-plane `LIKERTS_CALLBACK_STATUS_TOKEN` to the API's existing 32–512-character `LIKERTS_MONITOR_TOKEN`. That secret authorizes only internal metrics and the sanitized callback status route; it is not a management, collection, worker or maintenance credential. Missing callback configuration degrades the monitor. No checked-in deployment writes either value.
4. Add a Vercel Cron entry for `/api/monitor` at the owner-approved cadence (an initial five-minute cadence is a suggestion, not an active schedule), deploy and verify an authenticated invocation. The checked-in Vercel configuration currently has no cron entry. Missing/wrong `CRON_SECRET` returns 401; `not_armed`, `monitor_unavailable` and `retry_exhausted` are failures, not active coverage.
5. Exercise controlled failure and recovery probes, state/receiver failures, callback-worker process loss and a missing-run condition. An independent watcher must poll authenticated `/api/monitor-heartbeat`; reading it never advances the heartbeat. State older than twelve minutes is stale. A 2xx receiver reply proves transport acknowledgment only: record a separate human acknowledgment and escalation owner. The callback source proves recent successful queue polling and its database write, not delivery to a customer endpoint. Monitor DB capacity, private storage and deletion-journal lag separately; public probes do not cover them.

The optional [independent watcher configuration](observability/README.md) supplies a private Blackbox probe, separate Prometheus job and tested failure/absence rules. It is not deployed; independent hosting, an approved Alertmanager receiver and a provider dead-man check remain activation requirements.

Keep the actual state of each activation step and the next drill date in the H04 evidence. Do not configure an external receiver or send test notifications before that destination has been approved.

Run `bash scripts/check-observability.sh` to parse configuration and test healthy/idle, missing-target, sustained-error and high-latency cases using Prometheus 3.5.0. These tests do not prove notification delivery. For the Render launch target, add managed checks for database storage, connections, CPU, HA/failover state and backup freshness; API/worker health and restarts; private export errors; and deletion-journal replication lag. The optional AWS target uses corresponding RDS/ECS/S3 alarms. Explicitly fail an instance, the database connection, and the notification receiver to verify both primary and missing-monitor paths.

## Incident response

1. The responding engineer records UTC detection time, affected region and route, current image digest, migration version and observed customer impact. Assign incident lead and a second recovery reviewer before a data restore. Keep answers, tokens and connection strings out of incident notes.
2. Check public probes, per-instance scrapes, Render deploy/restart events, worker logs and Neon storage/compute/connections. Confirm whether a metric outage is an application outage or a scraper/token failure. Check accepted-response usage independently of HTTP request volume.
3. For an isolation, credential or accounting issue, stop affected collection writes and management mutations. Remove public ingress if scope is unknown. Revoke affected credentials and isolate suspect exports. Preserve restricted audit evidence. Do not re-enable writes merely because health is green.
4. For a deployment regression, roll back to a recorded compatible image digest using [README.md](README.md). Confirm that the previous binary supports every applied migration. An image rollback does not roll back the database. Prefer a reviewed forward fix; never edit an applied migration checksum in a live database.
5. Verify a synthetic tenant and a separate tenant: authorization denial across tenants, accepted response and identical retry, response counters, caps, response retrieval and export. Review audit events and rate-limit behavior. Only then restore traffic gradually and observe latency and errors.
6. Record resolution, actual recovery timing/data-loss window, corrective owner and next test date. Send customer or regulator communications only through the authorized incident owner and policy; this repository does not send them.

## Backup and restore discipline

The Render/Neon launch design requires the selected Neon backup/PITR policy, encryption, access control and a separately durable deletion journal. These deployment requirements still need hosted evidence; provider plan names and restore controls do not establish a recovery objective. A journal kept only inside the database being restored cannot prove post-snapshot deletions. Export download authorization expires after 24 hours; physical deletion requires verified cleanup. Restore must never resurrect revoked objects or download capabilities. The 22 September Console readback verified Neon Launch/Singapore with PostgreSQL 18 and a one-day history window; no manual snapshots or snapshot schedule were present. Access is available, while an actual quarantined restore/replay remains unverified. The owner declined execution of the [bounded drill plan](../docs/operations/NEON-RECOVERY-DRILL.md); it is retained only as a reference, with no compute provisioning or recovery-test spending authorized.

Restore into a quarantined database with no public traffic or callback workers. Preserve migration owner/runtime separation and forced RLS. Record the snapshot/PITR timestamp, last verified independent deletion-journal checkpoint and current credential/membership checkpoints. If the journal is incomplete, keep restored data inaccessible until the gap is reconciled. Replay all deletions after the recovery point before granting access. Workspace deletion also requires redacting its survey and response data, clearing management caches and preventing identity re-entry. Revoke restored exports and every old collection capability, OAuth grant and service credential; reissue only after reconciling current authoritative membership and revocation records.

Quarantine every restored callback endpoint and delete restored callback event/idempotency queues before starting callback workers: a snapshot can predate revocation or key rotation. Reconcile current ownership and issue fresh credentials; never resume an old queue automatically. The [callback runbook](webhooks/README.md) documents the worker boundary and signing-key procedure.

Reconcile restored accepted-response counters against retained response rows and deletion events before reopening collection traffic. Compare immutable response identifiers and idempotency records; rejected and duplicate submissions must not change usage.

Apply only the expected immutable migration set; compare SQLx checksums and test the candidate binary. Re-run RLS and scope tests against the restored database. Retain the quarantined original evidence under restricted access until the incident owner approves disposal under retention policy. Measure the entire path through safe reopening when reporting RTO; measure the actual recoverable data boundary when reporting RPO.

## Reproducible local drill

Run `bash scripts/check-recovery.sh`. Docker and Node are required. It builds the immutable runtime candidate and creates only isolated synthetic resources. The container gate first proves migrations, non-root/read-only runtime, restricted-role grants, RLS, authentication and restart durability. The drill then creates two accepted responses, an export and queued callback events, backs up PostgreSQL, deletes one response after the backup and captures the independent deletion journal. It restores to a new database, replays deletion and quarantines every restored capability, verifies the retained response and accepted-response counters, and proves old credentials, exports and callback queues cannot resume. It checks every applied migration, collection-security rate windows and forced RLS after restore.

The failed-migration drill uses a deliberately failing DDL transaction and proves no partial table or migration-state advance. A separate checksum-mismatch drill proves the migration runner refuses altered history. Only this disposable restored copy has its checksum deliberately modified and restored. This is not a production recovery technique.

[recovery/replay.sql](recovery/replay.sql) refuses databases outside the `likerts_recovery_*` namespace. It is a fixture for testing quarantine/replay, not an automated production restore command. It exercises response deletion and a second workspace's tombstoning and survey/version redaction. All local resources created by the harness are removed on completion, including PostgreSQL's anonymous data volume. The written JSON evidence remains available for review. Use `LIKERTS_SKIP_IMAGE_BUILD=1` only when intentionally testing the already-built digest, and record that digest with the result.

Before making managed recovery claims, execute a Neon restore/PITR recovery including workspace deletion, revoked memberships and expired private export objects. Prove journal checkpoint freshness and the configured backup policy, measure recovery bounds, exercise a migration failure and compatible Render image rollback, and deliver a real test alert to the owned receiver.
