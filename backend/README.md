# Likerts Rust foundation

Service foundation. This process binds to loopback by default and uses PostgreSQL when `DATABASE_URL` is set; volatile memory requires an explicit development switch. It includes test-mode payment settlement but has not passed the real Stripe sandbox gate. PostgreSQL mode accepts hashed tenant-bound service credentials and provider-neutral verified OIDC JWT access tokens, then rechecks durable grants and current roles on every request. Customer membership, OAuth-grant and service-credential operations are exposed with owner-only `identity:write` authority. Clerk sandbox and production infrastructure validation remain open.

Run with a current stable Rust toolchain:

```sh
export LIKERTS_DEV_TOKENS='{"local-development-token-a":"workspace-a","local-development-token-b":"workspace-b"}'
export LIKERTS_ALLOW_DEV_AUTH=1
export DATABASE_URL='postgres://likerts:development-password@127.0.0.1:5432/likerts'
export LIKERTS_COLLECTION_CREDENTIAL_KEY="$(openssl rand -base64 32)"
export LIKERTS_RUN_MIGRATIONS=1
cargo run --manifest-path backend/Cargo.toml
```

For multi-replica staging, set `LIKERTS_EXPORT_BUCKET`, AWS region/task-role credentials and `LIKERTS_REQUIRE_S3=1`. `LIKERTS_EXPORT_PREFIX` defaults to `exports`. Without these settings, exports use the local filesystem for development and isolated container tests.

`LIKERTS_PORT` defaults to 8080. Migrations run on startup only when `LIKERTS_RUN_MIGRATIONS=1`; use that with a migration-capable local account. Production runs migrations as a separate job and connects the service with the restricted role described in `provision-runtime.sql`. Development token maps require `LIKERTS_ALLOW_DEV_AUTH=1`; memory mode implies development auth and requires at least one mapped token. PostgreSQL production mode can start without static tokens and authenticates provisioned service credentials. A disposable memory run requires `LIKERTS_ALLOW_MEMORY=1`; missing durable configuration otherwise stops startup.

Human OAuth requires `LIKERTS_OIDC_ISSUER`, `LIKERTS_OIDC_AUDIENCE` and `LIKERTS_OIDC_JWKS_URL` together. Configure the issuer exactly as it appears in access-token `iss` and authorization-server metadata; do not add or remove a trailing slash. The JWKS URL is an explicit HTTPS trust input rather than a derived provider path. The local verifier accepts RS256 JWT access tokens with `client_id` or a matching compatibility `azp`; opaque access tokens require an online provider verifier and are not accepted.

Management requests use `Authorization: Bearer <management token>`. Service credentials map to exactly one workspace, store only a SHA-256 digest, expire within one year and carry explicit scopes including `surveys:read`, `surveys:write`, `collections:write`, `responses:read`, `responses:write`, `exports:read`, `exports:write`, `usage:read` and `identity:write`. Missing scope returns 403; expiry, revocation and invalid credentials return 401. Static token maps grant all operations and exist only behind the explicit development switch. Collection creation returns a separate submission/schema-only bearer token. Never place a management token in a client application.

All wire fields use camelCase. SDK schema fetch is `GET /v1/collections/{id}` and response submission is `POST /v1/collections/{id}/responses`. Both require that collection's token. Collection tokens cannot read responses or usage. There are no hosted survey pages or distribution endpoints.

Survey creation requires `{idempotencyKey,title,questions}`; collection creation also requires `idempotencyKey`. Keys are nonblank, at most 128 characters and scoped to workspace plus operation. Identical retries return the original response, including the original collection credential; changing the payload for a used key returns a conflict. Survey drafts require a title and 1–100 questions. Supported question types: `single_choice`, `multiple_choice`, `scale`, `text`, `number`, `date`, `ranking`, `matrix` and `constant_sum`. Text requires `maxLength` from 1–10000; scale requires integer `min`/`max` from -1000 to 1000; choice options are `{id,label}`. Missing optional answers are omitted rather than null. Required text cannot be blank. Metadata is untrusted, capped at 4096 encoded bytes; request bodies are capped at 64 KiB.

The first enhancements retain the six baseline answer types: `preset: "nps"` requires a 0–10 scale; `preset: "yes_no"` requires single choice with exactly `yes` and `no` option IDs (labels are configurable). Scales accept a `labels` map with canonical integer keys inside their bounds and nonblank labels up to 500 characters. Multiple choice accepts integer `minSelections`/`maxSelections`, bounded by its option count; required questions require at least one selection. Optional answers may be omitted, but a supplied array must satisfy its limits. Unsupported properties and explicit null configuration fields are rejected. These first enhancements require at least schema version 2; baseline-only surveys use version 1. Later features raise the version further. Published schema and collection bindings remain immutable.

Schema version 3 adds `visibleWhen` with one source and one of `equals`, `not_equals`, `includes`, `not_includes`, `answered` or `not_answered`. Draft validation rejects invalid references, source/operator/value combinations and dependency cycles. Comparison operators are false without an effective source answer; answered text is trimmed. Hidden questions are not required, and hidden answers are removed before validation and persistence. See `../contracts/CONDITIONAL-VISIBILITY.md` for the complete cross-platform semantics and fixture.

Schema version 3 also adds Other/exclusive options and stars/dropdown presentations; schema version 4 adds pages and bounded forward routes. See [choice semantics](../contracts/CHOICE-FEATURES.md) and [page routing](../contracts/PAGES-AND-BRANCHING.md).

Schema version 5 adds ranking, matrix and constant-sum questions. Ranking uses 2–50 plain choices and requires a complete unique permutation. Matrix questions use 1–50 rows, 2–20 columns, at most 200 cells and either single or multiple mode; required answers cover every row. Constant-sum questions use 2–50 items and an integer total from 1–1,000,000; a supplied answer contains every item, uses nonnegative integers and sums exactly to the total. See `../contracts/ADVANCED-QUESTIONS.md` for immutable wire semantics, mobile controls and limits.

Publishing freezes the current draft revision as its version number; publishing that revision again requires the identical capability declaration and returns the same version. Publish and collection creation require `sdkCapabilities.installations`, where each customer-declared group contains `target`, `sdkVersion` and `schemaVersions`. Every group must support the actual schema version. A mixed fleet with any v1-only installation therefore cannot publish or bind a v2 survey. Declarations are persisted on both immutable resources as rollout evidence; they do not attest installed code.

Collection bindings are immutable. Creation optionally accepts `expiresAt` (future, at most 90 days) and `responseCap` (positive integer). A workspace may have 100 active, unexpired collections. `PATCH /v1/collections/{id}` accepts exactly one of `{accepting}` or `{revoke:true}`. Revocation is irreversible and denies schema access and prior retries; ordinary closure and expiry preserve identical prior receipts.

Submission uses `{idempotencyKey,answers,metadata?}`. In PostgreSQL mode, response acceptance and its one-cent usage entry commit in one transaction under a database uniqueness constraint. Identical concurrent retries return the same durable receipt, including after a collection closes and after the current rate window is exhausted; changed payloads conflict. A receipt's `chargedCents: 1` describes the single acceptance entry, not an additional charge on retry. Collection credentials are derived with `LIKERTS_COLLECTION_CREDENTIAL_KEY`; PostgreSQL stores only their digest and never writes the recoverable credential into a management retry row. Keep this 32-byte base64 key in the deployment secret manager and stable for every active collection.

`GET /v1/usage` reports lifetime and current UTC-month usage, the workspace's monthly-spend and unpaid-exposure caps, remaining cents, and whether paid acceptance is available. Both caps default to 500 cents. `PATCH /v1/billing/limits` changes either cap independently with `billing:write` owner access; zero pauses new acceptance. A workspace billing lock serializes concurrent submissions before the response and usage entry commit, so excess work receives `402 spend_limit_reached` without billing while valid prior retries still succeed. Unpaid exposure subtracts successful settlements and incorporates immutable adjustments; lifetime response usage remains unchanged. See `../BILLING-LIMITS.md`.

The prepaid purchase path uses `POST /v1/billing/checkout` and the browser checkout route. `POST /v1/webhooks/stripe` verifies Stripe's timestamped HMAC before binding a PaymentIntent, crediting a purchase or reconciling cumulative refunds/disputes. Provider withholding is append-only, cannot exceed the original purchase, and may produce signed paid-credit debt after consumption; debt pauses new acceptance without rewriting usage. Historical postpaid settlement routes remain for compatibility and are not the public launch model. See `../STRIPE-SANDBOX.md` for the real hosted test-mode checkout evidence and remaining live-mode gates.

Management response retrieval is `GET /v1/responses`. It returns `{items,nextCursor}` in immutable acceptance order, with a default page size of 100 and a maximum of 1,000. Optional `collectionId`, inclusive `acceptedFrom` and exclusive `acceptedTo` filters apply to the first page. Pass the returned opaque `nextCursor` to continue; it preserves the original page size, filters and snapshot boundary, so responses accepted during traversal appear only in a new traversal. Repeating a page request is deterministic. A cursor may be supplied with its original filters, but changing a filter or page size is rejected. PostgreSQL submission/list advisory locks establish the first-page boundary without serializing ordinary submissions with each other. Every query remains inside the transaction-local workspace RLS scope.

`POST /v1/exports` accepts `{idempotencyKey,format,collectionId?,acceptedFrom?,acceptedTo?}` for `csv` or `json`. It records the same stable response boundary before returning HTTP 202, then a background worker claims and generates the job. Poll `GET /v1/exports/{id}` until `status` is `ready` or `failed`; an identical create retry returns the same job and requeues a failed job, while changed input conflicts. Export jobs allow at most 100,000 responses and 64 MiB of output. Their manifest fixes the filters, response count, snapshot sequence and every referenced immutable survey schema. JSON embeds the manifest and responses. CSV has fixed receipt/time/JSON columns; all cells are quoted, dangerous spreadsheet formula prefixes are neutralized, and user answer/metadata values remain JSON-encoded.

`GET /v1/exports/{id}/download` requires `exports:read` access and returns the content as base64 with its media type, SHA-256 digest and manifest, which keeps API, MCP and CLI behavior identical. Downloads expire 24 hours after job creation. `DELETE /v1/exports/{id}` requires `exports:write`, irreversibly revokes access and deletes the object. Set `LIKERTS_EXPORT_BUCKET` and `LIKERTS_REQUIRE_S3=1` for the asynchronous private-S3 implementation used by multi-replica staging; the bounded local store remains for development and isolated gates.

`DELETE /v1/responses/{id}` erases raw answers and metadata, revokes every export that could contain the response and deletes those objects while retaining the original receipt, capability-keyed payload digest and immutable usage. `POST /v1/retention` runs at most 1,000 due responses and 1,000 expired or affected exports for the authenticated workspace. `DELETE /v1/workspace` tombstones the account, revokes collection and export capabilities, removes identity and management retry records, and redacts respondent and survey content while preserving accounting. All three operations are available through the same API/MCP/CLI registry. See `../DATA-LIFECYCLE.md` for the 90-day raw-data default, 24-hour exports, seven-day backup expiry and mandatory deletion replay after restore.

Run `cargo test --manifest-path backend/Cargo.toml` for domain checks and `bash scripts/check-postgres.sh` for isolated persistence, restricted-role RLS, rollback, restart, idempotency, collection-control races, concurrent pagination, export job failure/retry/expiry and full deletion/retention lifecycle tests. Before production: complete traffic abuse protection; CORS policy for browser integrations; private S3 lifecycle configuration; managed backup restore/deletion replay; audit and observability; HTTPS and secret management. No unrestricted CORS policy is installed in this prototype; use a same-origin development proxy for Web SDK integration.
