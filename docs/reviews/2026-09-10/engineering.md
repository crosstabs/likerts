# Engineering readiness review — 10 September 2026

**Verdict: HOLD public paid launch. Continue a supported developer preview after correcting the customer-flow and public-example defects below.** The collection engine is substantially implemented; the largest remaining work is proving the customer journey and operating it safely on the deployed providers. Do not rebuild tenant isolation, the response ledger, or the five SDK foundations simply because their final release gates remain open.

## What is already real

- **Isolation and authorization:** the repository has transaction-local workspace context (`backend/src/postgres.rs:203`), durable workspace membership, scoped credentials and restricted database roles. Recorded hosted tenant binding permits the correct workspace and rejects a mismatched workspace through API and MCP; deleting the workspace invalidates the credential. Evidence: `LAUNCH-DECISION.md:15`, `infrastructure/render/hosted-evidence.json:76`. No tenant leak was found in this bounded review; this does not certify all access paths.
- **Core hosted lifecycle:** credential issue/revoke, immutable survey publication, collection submission/retrieval, private export/download, deletion-triggered export revocation and tombstoning have an explicit hosted evidence record. `infrastructure/render/hosted-lifecycle-evidence.json:2` records one accepted response and one promotional credit consumed.
- **Accounting:** one-time onboarding, atomic prepaid consumption and retry deduplication have local restricted-role evidence. The real hosted sandbox purchase/refund preserved 1,000 promotional credits and removed exactly 500 purchased credits without debt (`infrastructure/render/hosted-refund-evidence.json:2`). This is test-mode evidence, not live settlement.
- **Interface coverage:** the recorded gate covers 40 product operations across API/MCP/CLI and 53 HTTP routes (`LAUNCH-DECISION.md:20`). A real Codex/Claude customer connection is a separate missing acceptance step, not proof those adapters are absent.
- **All five SDKs:** frozen 0.0.3 artifacts support schemas 1–5; clean-consumer checks exist for each target (`releases/0.0.3/manifest.json:2`, `:44`). Direct checksummed downloads are usable today. Registry publication and the supported device/accessibility matrix are not complete (`TASKS.md:63`).
- **Operations foundations:** hosted compatible rollback, rejected deployment candidate, signed ID-only callbacks, redirect denial, timeout scheduling and two-worker delivery have recorded evidence. Local backup/restore, deletion replay and quarantine tests exist. These are useful foundations, but graceful restart is not abrupt-failure recovery (`LAUNCH-DECISION.md:22`, `infrastructure/render/hosted-evidence.json:299`).

## Verified defects and misleading surfaces

### E-01 — Checkout returns to the marketing page after the `/app` split

`backend/src/billing.rs:265` and `:269` generate `/?checkout=success` and `/?checkout=cancelled`. Only the console script handles those parameters (`control-plane/public/app.js:167`); the homepage now loads only `marketing.js` (`control-plane/public/index.html:11`). Consequently a completed/cancelled checkout returns to marketing, away from the balance and checkout state. The ledger webhook is independent, so this does **not** demonstrate lost credits or failed payment settlement.

The same console also treats the URL query as “Payment received” and loads usage just once (`app.js:169`, `:203`). A forged query or delayed webhook can therefore show unsupported success/stale balance. The proper completion state must come from the purchase/credit API.

### E-02 — Public CLI/API examples do not run against the shipped contract

`control-plane/public/marketing.js:17` advertises `likerts survey create --file`, `likerts collection issue`, and `likerts usage`; the CLI accepts `likerts call <capability> [--input <file|->]` (`tools/cli/src/main.rs:523`). A targeted local invocation of the advertised first command exited 1 with that actual usage message before any network call.

The API example at `marketing.js:18` and hero sample at `index.html:35` use `type: "likert"` / `scale: 5`; the contract uses `type: "scale"`, question `id` and `label`, and `min` / `max`. Survey creation also requires `idempotencyKey`. The authoritative example is `contracts/examples/surveys_create.input.json:1`. The marketing request cannot legitimately produce the shown `201 Created`.

The preview at `index.html:73` additionally promises “If score ≤ 3, ask why”; the current single-predicate language supports equality, inclusion and answered state, not numeric ordering (`contracts/CONDITIONAL-VISIBILITY.md:9`, `backend/src/conditional.rs:45`). Correct the example to an implemented condition. Adding a new operator across all five SDKs is unnecessary launch scope.

### E-03 — “Service status” is a configuration document

The public link at `control-plane/public/index.html:89` leads to `/api/health`. That handler always reports `status: "ok"` and only tests whether two environment values exist (`control-plane/api/health.js:3`). It does not test API, database, payment or identity reachability. Keep it as configuration diagnostics or replace the public link with an actual status surface; do not interpret it as end-to-end uptime.

### E-04 — CI is blocked before execution

Rechecked the latest run [34356596007](https://github.com/crosstabs/likerts/actions/runs/34356596007) for the reviewed commit. Both jobs have no steps. GitHub's check-run annotation says: “The job was not started because recent account payments have failed or your spending limit needs to be increased.” This confirms an account/budget blocker, not a new test failure. Local green checks cannot be described as remotely enforced release checks.

## Unverified gates, not demonstrated bugs

- **Actual identity onboarding:** rendered Clerk sign-in is not a completed OTP signup, recovery, workspace bootstrap or session removal. `app.js:205` mounts sign-in without an explicit `/app` completion destination. Provider defaults may redirect correctly or incorrectly; this review did not prove either. Test the new route after real sign-in and sign-up (`TASKS.md:32`, `release/acceptance/README.md:23`).
- **Preview access restrictions:** docs say invite-only, but the visible bootstrap provisions any valid subject it accepts (`backend/src/main.rs:668`, `backend/src/postgres.rs:293`). Clerk's external signup restrictions were not inspected. There is no evidence here that the public preview is technically invitation-gated.
- **Grant abuse:** deterministic per-subject workspace identity and transactional once-only grants prevent same-account replay; they do not establish resistance to one person registering many identities. The open signup/admission controls remain material with a free grant (`TASKS.md:52`).
- **OAuth:** scoped service credentials work in recorded hosted flows. Provider consent, token shape, refresh/revocation/JWKS rotation and actual Codex/Claude client acceptance remain open (`TASKS.md:36`). Do not call the full OAuth journey finished or mistake browser session tokens for management tokens.
- **Managed recovery:** no successful Neon managed restore is recorded; the console required Marketplace email verification (`infrastructure/render/hosted-evidence.json:309`). Export and callback tests recorded unchanged original leases after graceful restarts, so hard-loss reclaim is still unproved (`:301`, `:443`).
- **Callback boundary:** DNS address checks and HTTP controls are implemented, with useful hosted tests; customer-owned DNS, dynamic rebinding, deployed outbound enforcement and delivered worker alerts remain unverified (`infrastructure/render/hosted-evidence.json:375`).
- **Monitoring:** the runbook explicitly says no active pager/cloud backup schedule/customer SLA (`infrastructure/OPERATIONS.md:3`). Rules parsing is not a delivered alert. Parts of the runbook still describe ECS/ALB/RDS (`:11`, `:18`) while launch uses Render/Neon.
- **Live money and scale:** hosted payments are sandbox-only. Refund/dispute ordering still needs provider acceptance. Bounded 5-RPS/short-burst evidence does not establish sustained capacity or profitable unit economics (`TASKS.md:53`, `:80`).
