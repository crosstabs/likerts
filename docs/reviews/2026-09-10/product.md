# Product review — 10 September 2026

## Decision

**Keep the developer preview limited and assisted. Hold public paid launch.** The collection engine has meaningful implementation and hosted lifecycle evidence. The missing product work is the path from a new visitor to a successful, independently operated integration. A rendered sign-in screen, downloadable archive, or successful service-token rehearsal does not prove that path.

The first release should remain collection infrastructure: customer-owned distribution; API, MCP and CLI management; Web, React Native, iOS, Android and Flutter. A GUI survey builder is not required.

This review inspected the existing code graph, verified relevant findings against source, read launch/acceptance artifacts and performed unauthenticated HTTP checks. It did not create an account, connect a customer agent, submit a response, purchase credits or certify native devices. Paths and line numbers below refer to the reviewed working tree. Effort estimates are working days for the named workstream, exclude external account/legal delays, and are not commitments.

## What is real today

- Hosted service-token evidence covers create → publish → collection configuration → one accepted response → retrieve → private export → delete → revoke → workspace tombstone. See `infrastructure/render/hosted-lifecycle-evidence.json:4`.
- One-time grants, scope enforcement, idempotency, immutable publication, answer validation and prepaid accounting have local and bounded hosted evidence. These foundations should not be rebuilt.
- All five SDK 0.0.3 archives and a CLI source archive have a public download path. Clean-consumer verification is separate from actual supported-device acceptance (`sdks/INSTALLATION.md:13`, `:23`, `:31`).
- The existing customer acceptance runner is deliberately honest about its boundary: it does not perform inbox, real client, payment or operator steps (`release/acceptance/README.md:5`). Use it to finish acceptance instead of adding another synthetic happy-path script.

## Acceptance records to correct

1. `LAUNCH-DECISION.md` says the hosted lifecycle passes “five-SDK collection.” The referenced evidence records **five-SDK capability declaration accepted** and **one response** (`infrastructure/render/hosted-lifecycle-evidence.json:7–9`). Actual all-five-SDK execution belongs to the local rehearsal. Preserve that distinction.
2. The four control-plane tests verify build, CSP, file existence and source strings (`control-plane/test/control-plane.test.mjs:28–115`). They do not verify OTP, post-auth navigation, token issue/revoke, checkout return or first response. “4/4 tests pass” is insufficient customer journey evidence.
3. `sdks/BEHAVIOR-CONTRACT.md:21` still says only schemas 1 and 2 are supported, while current artifacts support 1–5. `control-plane/README.md:13` still describes a replacement/deployment sequence that already happened. Acceptance and setup docs also point to the homepage rather than the now-separated `/app`.
4. No human journey evidence should be inferred from the acceptance runner's presence. Its own checklist explicitly requires recorded OTP, grant relogin, real Codex and real Claude Code observations.

## What not to add before launch

Do not add a drag-and-drop survey builder, analytics dashboard, email distribution, public survey links, enterprise SSO, dedicated tenancy, auto-top-up, an AI question generator or additional question types to solve these gaps. Existing question breadth is already sufficient. Provider OAuth can remain an explicitly deferred path while scoped service credentials support verified customer clients. Package registries improve adoption but need not block an assisted preview that has complete public installation instructions.

The fastest credible release sequence is: correct examples and checkout → finish real identity/agent acceptance → publish and test the first-response guide → validate all five supported hosts → complete live billing, policy and operational gates → open paid self-service.
