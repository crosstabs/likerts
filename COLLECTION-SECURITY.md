# Collection security contract

Collection credentials are public capabilities intended only for one immutable survey binding. They can fetch that binding and submit responses; they cannot manage surveys, retrieve results, export data or read usage. PostgreSQL stores only their SHA-256 digest and forced RLS admits a capability lookup only when the transaction supplies the matching digest. Expiry, closure, response caps, spend caps and irreversible revocation remain authoritative server checks.

Each collection has an explicit browser policy configured through `collections_security_update`. `allowedOrigins` contains at most 20 canonical exact origins. Production origins must use HTTPS; loopback HTTP is accepted for local development. Browser preflight discloses only whether a high-entropy collection ID permits the exact origin. Actual GET and POST requests still require the collection bearer credential. Allowed origins are CORS policy and never identity or authorization. Responses vary on `Origin`, rejected origins receive 403, redirects remain disabled in SDKs, and no wildcard or credentialed-cookie CORS mode exists.

`requestsPerMinute` defaults to 6,000 and may be configured from 1 to 100,000. A PostgreSQL row keyed by workspace, collection and UTC minute consumes an attempt atomically after the capability is verified and before answer validation or billing. Attempts above the bound receive HTTP 429 with `Retry-After: 60`. Invalid attempts still consume the bound and never create usage. An identical retry for an already accepted idempotency key returns its terminal receipt before consuming the limiter; changed payload reuse still returns 409 and a new key remains rate-limited. Old windows are deleted opportunistically after one hour.

Render automatically places every hosted web service behind Cloudflare-backed DDoS protection. That filters network floods and obvious high-volume HTTP attacks before the API, but it does not distinguish targeted, legitimate-looking application abuse. The collection-wide database limiter above is distributed across both API replicas only after a valid capability resolves. Before public self-service launch, add a distributed client-IP admission control for invalid credentials and other authentication-heavy entry points; use Render's forwarded client address only under the explicit hosted proxy configuration, store a keyed digest rather than the address, bound retained windows, and test spoofing and multi-replica enforcement. [Render DDoS protection](https://render.com/docs/ddos-protection) · [Render application-abuse guidance](https://render.com/articles/how-render-handles-ddos-attacks)

Every respondent-provided `metadata` value is untrusted client context. It is size-bounded, stored and exported as data, and never changes authorization, billing, tenant selection, rate limits or validation. Likerts v1 has no trusted/signed-context field. Customers needing server-attested attributes should store them in their own system keyed by the returned response ID. A future signed-context feature must use a separate typed field, versioned canonical encoding, a customer-managed verification key, expiry and nonce/audience binding; it must never silently reinterpret existing metadata.

The integration gate covers allowed and denied preflight, CORS headers on validation and 429 responses, invalid attempts followed by a rate denial, unchanged usage, and terminal retry delivery after rate exhaustion. Restricted-role PostgreSQL tests cover exact-origin lookup, atomic limit exhaustion, terminal retry lookup and unscoped RLS denial.
