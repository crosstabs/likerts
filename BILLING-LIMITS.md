# Response credits and usage

The local credit ledger is implemented and verified. [PRICING.md](PRICING.md) governs commercial policy. Verified signup and duplicate-workspace abuse controls, balance threshold notifications, payment-confirmed purchases and automatic top-up remain launch work under BILL-01/BILL-02.

Each live workspace receives one nonrenewing 1,000-response promotional grant, keyed `onboarding_v1`. PostgreSQL issues it during workspace creation or lazily initializes an older workspace. Concurrent retries cannot repeat it. Deleting a workspace preserves the ledger and tombstone, and cannot reset that workspace's grant. This is a per-workspace guarantee; preventing a person from creating multiple new workspaces requires the unfinished signup controls.

Acceptance consumes one promotional credit first, otherwise one paid credit. The collection lock and workspace billing advisory lock serialize checks; the response, credit debit, gross usage and webhook outbox commit in one transaction. Invalid, rejected and identical duplicate submissions consume nothing. At zero available credits new submissions return HTTP 402 `spend_limit`; `usage_get.blockedReason` is `credits_exhausted`. Existing reads, exports and valid prior receipts remain available, subject to normal access, expiry and revocation rules.

`usage_get` and `billing_limits_update` expose `credits`: promotional, paid and total available credits; lifetime promotional/paid responses; and current UTC-month paid responses. These fields have the same typed contract through API, MCP and CLI. The legacy `acceptingPaidResponses` field reports whether either balance can fund acceptance. Receipt `chargedCents: 1` and usage cents represent immutable gross service units, not an additional cash charge for a promotional or prepaid response.

The default monthly cap is 500 cents and applies to paid-credit consumption; promotional consumption bypasses this cap. A zero monthly cap blocks paid consumption only. The separate unpaid-exposure cap remains visible for historical accounts and does not govern prepaid acceptance. A durable billing pause still blocks new acceptance. Changing either cap leaves the other unchanged.

Migration 0018 creates an append-only, forced-RLS ledger with grant, purchase, consumption, refund, reversal and correction entries. Runtime can insert only one-credit consumption rows and invoke the fixed onboarding grant; it cannot mint paid credits. An internal migration-owner-only repository method records validated operator adjustments with exact idempotency. This method is not a public capability or proof of payment. Refunds debit only available paid balance against an original purchase and cannot exceed it. A reversal exactly negates an eligible original entry; an already-refunded purchase cannot be reversed. Insufficient balances fail closed. Every entry produces an ID-only audit event. Worker credentials cannot read the ledger.

Existing usage is preserved. Legacy postpaid settlement explicitly excludes every credit-funded response, preventing double charging. Historical settlement/refund tests seed separate pre-credit usage and retain their original accounting behavior. Raw-response deletion does not delete financial or deduplication records.

Verification: `bash scripts/check-response-credits.sh` runs memory and real restricted-role PostgreSQL cases for 1,000-credit exhaustion, invalid work, same-key retries, paid concurrency across collections, injected transactional failure, restart, refunds/reversals, tenant denial, direct SQL mint denial, append-only enforcement, audit and deletion/recreation denial. `scripts/check-postgres.sh` covers collection-close races and legacy settlement exclusion. Real CLI→MCP→Web integration and `contracts/check-release.mjs` verify the public usage contract. `scripts/check-render-roles.sh` verifies the fixed grant under a non-superuser migration owner. Hosted load, financial retention policy, checkout reconciliation and abuse prevention are not established by these local checks.
