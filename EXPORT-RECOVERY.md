# Recovering interrupted exports

Export execution uses a durable five-minute lease and a unique attempt UUID. The database grants one current lease; reading the snapshot, publishing its object and reporting failure require that lease. Execution has a four-minute timeout. An expired or superseded attempt cannot publish, fail the replacement or overwrite its object: each attempt writes a distinct private object key.

Recovery is driven by authenticated customer requests. Polling `exports_get` schedules queued work or reclaims an expired running attempt. Retrying `exports_create` with the original idempotency key preserves its job ID, filters, snapshot boundary and original 24-hour expiry. Creating a different export reaps expired running leases and queued reservations older than five minutes before checking the one-active-export limit. Retrying a failed old job while another job is active returns the ordinary capacity error. There is no autonomous cross-tenant scheduler; without further polling or retry, interrupted work waits.

These operations use the caller's workspace context and existing forced RLS. Lease recovery does not introduce global tenant enumeration or new runtime grants. Revocation, response deletion, workspace deletion and export expiry still prevent a late completion from publishing data. Status polling requires `exports:read` and resumes only a previously authorized job; it cannot create a new export definition.

After a failed attempt, execution removes only its own unpublished object. If a database commit is ambiguous or the database is unavailable, cleanup preserves a potentially published object and relies on private object expiry. A hard process termination between object upload and database publication may leave an unreachable private attempt object until provider lifecycle cleanup. Hosted object-expiry enforcement remains an operations gate.

Migration 0019 retains tenant isolation while supporting pre-migration running jobs with no lease. Such jobs are treated as abandoned when next claimed or reaped. Its running-job constraint is `NOT VALID` for those existing rows under forced RLS; new and updated rows are checked. Drain old export executors before applying/promoting this version because old binaries do not fence their publication. The lease is internal and does not change the public job schema.

Verification: `bash scripts/check-export-leases.sh` uses a fresh PostgreSQL database and the canonical restricted runtime grants. It models a lost executor by closing its connection pool after durable claim, races eight replacements, checks stale completion/failure and tenant denial, proves reservation recovery and revocation, and starts a replacement HTTP API whose authorized status polling finishes an abandoned job. The Rust memory test `export_lease_fences_stale_completion_and_reaps_capacity` checks equivalent ownership behavior. `scripts/check-postgres.sh` and real interface integration cover the existing export lifecycle and immutable snapshots. Local tests do not establish hosted failover latency or an autonomous scheduler.
